# ADR-0005: CI/CD, versionamento e deploy

- **Status:** Proposto (em discussão — Épico 11)
- **Data:** 2026-08-07
- **Contexto de decisão:** Épico 11 — DevOps

## Contexto

Precisamos de builds confiáveis, testes automáticos em cada PR e deploy do backend (Render) e
do frontend (Vercel). Queremos versões identificáveis para o relatório acadêmico e para o vídeo.

## Decisão (proposta, a validar)

**CI (GitHub Actions), roda em todo PR e push para `main`:**

- Job **backend**: setup JDK, cache Maven/Gradle, `build` + `test` (JUnit/Mockito/Spring Test),
  relatório de cobertura, build da imagem Docker.
- Job **frontend**: setup Node, cache, `lint` + `test` (Vitest/RTL) + `build`; e2e (Playwright)
  em job separado/nightly para não travar o PR.
- CI é **status check obrigatório** para merge (ver ADR-0004).

**Versionamento:**

- **SemVer** (`MAJOR.MINOR.PATCH`) via tags Git (`v0.1.0`, …).
- Tag em `main` dispara build da versão e gera **release** no GitHub com changelog.

**CD (deploy):**

- **Frontend → Vercel:** integração nativa com o GitHub (deploy automático da `main`; previews por PR).
- **Backend → Render:** deploy a partir da imagem Docker/branch `main`; migrations Flyway rodam no start.
- **Banco → Neon:** um projeto por ambiente (ao menos `prod`; opcional `preview`/branching do Neon).
- Segredos (JWT secret, URL do banco) em **secrets** do GitHub/Render/Vercel — nunca no repo.

**Ambientes:** começar com `prod` único; avaliar `staging` conforme necessidade.

## Alternativas consideradas

- **Deploy manual:** simples, mas propenso a erro e sem rastreabilidade. Descartado para o fluxo padrão.
- **Só CI, sem CD automático:** possível no início; a decisão de automatizar o deploy fica para a discussão do Épico 11.

## Pontos em aberto (a decidir juntos)

- Maven ou Gradle no backend?
- Deploy automático em cada merge, ou promover manualmente por tag?
- Precisamos de ambiente `staging` antes de mostrar à secretaria?
- Playwright no PR (mais lento) ou só nightly?

## Consequências

- Positivas: qualidade garantida por PR, versões rastreáveis, deploy reproduzível.
- Negativas: setup inicial de workflows e segredos; e2e pode alongar o CI (mitigado separando o job).
