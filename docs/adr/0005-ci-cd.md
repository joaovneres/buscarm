# ADR-0005: CI/CD, versionamento e deploy

- **Status:** Aceito
- **Data:** 2026-08-07
- **Contexto de decisão:** Épico 11 — DevOps

## Contexto

Precisamos de builds confiáveis, testes automáticos em cada PR e deploy do backend (Render) e
do frontend (Vercel). Queremos versões identificáveis para o relatório acadêmico e para o vídeo,
e controle sobre **quando** cada versão vai para produção (demos com a secretaria).

## Decisão

Três pipelines separadas no **GitHub Actions**:

### 1. CI — `.github/workflows/ci.yml` (em todo PR e push na `main`)
- Job **backend**: JDK 21 (temurin) + **Maven** (`mvn -B verify`) → build + testes (JUnit/Mockito/Spring Test), cache Maven.
- Job **frontend**: Node 20 → `lint` + `test` (Vitest/RTL) + `build`, cache npm.
- Job **e2e**: **Playwright em todo PR** (após backend e frontend), garantindo o fluxo principal.
- Os três são **status checks obrigatórios** para merge na `main` (ADR-0004).

### 2. Release/Build — `.github/workflows/release.yml` (ao criar tag `vX.Y.Z`)
- **Versionamento SemVer** por tag Git.
- Gera **automaticamente** a **imagem Docker versionada** do backend e publica no **GHCR**
  (`ghcr.io/<owner>/buscarm-backend:vX.Y.Z` + `:latest`).
- Gera o **build do frontend** (artefato) e um **release** no GitHub.
- Este passo **não** faz deploy — apenas produz o artefato/imagem versionado.

### 3. Deploy — automático a partir do Git (ver **Atualização 2026-08-24**)
- **Backend (Render):** serviço `docker` conectado ao repo (`rootDir: backend`, `branch: main`,
  `autoDeploy: on`) — o Render **builda o `backend/Dockerfile` e publica a cada push na `main`**.
- **Frontend (Vercel):** projeto conectado ao repo — a Vercel **rebuilda e publica a cada push
  na `main`** (produção) e gera preview por PR.
- Migrations **Flyway** rodam no start do backend.
- **Verificação pós-deploy:** `.github/workflows/smoke.yml` (`workflow_dispatch`) confere
  `/actuator/health` do backend e a URL do frontend (T11.7).

**Ambientes:** produção única (a `main`).
**Segredos:** runtime (`JWT_SECRET`, `DATABASE_URL`, `ADMIN_*`, `CORS_ALLOWED_ORIGINS`) nos painéis
do **Render/Vercel**; nada de segredo no repo. Não há deploy hooks — o gatilho é o próprio push.

## Alternativas consideradas

- **Deploy automático em cada merge:** contínuo, porém tira o controle de quando mostrar uma
  versão à secretaria. Preferimos **build automático + deploy manual** por versão.
- **E2E só nightly:** deixaria o PR mais rápido, mas optamos por rodar Playwright em **todo PR**
  para máxima garantia do fluxo crítico (trade-off: PR mais lento).
- **Gradle:** descartado em favor de **Maven** (mais comum em Spring/contexto acadêmico, exemplos abundantes).
- **Deploy manual sem pipeline:** propenso a erro e sem rastreabilidade. Descartado.

## Consequências

- Positivas: qualidade garantida por PR (inclui e2e), versões rastreáveis por tag/imagem,
  deploy reproduzível e sob controle humano.
- Negativas: e2e alonga o CI de cada PR (mitigar cuidando de flakiness); deploy manual exige um
  passo humano por release (aceitável e desejado aqui).
- Observação: os checks `backend`/`frontend`/`e2e` só passam a existir e a ser exigidos após o
  scaffold do backend (Épico 2) e do frontend (Épico 4) e a primeira execução no GitHub.

## Atualização (2026-08-24)

A decisão original previa **deploy manual versionado** (`deploy.yml` disparando *deploy hooks* do
Render/Vercel apontando para a imagem GHCR). Na prática, o provisionamento seguiu por **conexão
direta ao Git**: o Render foi criado como serviço Docker ligado ao repo (build do
`backend/Dockerfile`, `autoDeploy: on`) e a Vercel como projeto ligado ao repo — ambos
**publicam sozinhos a cada push na `main`**. Isso já era uma alternativa antecipada em
`CONFIGURACAO_NUVEM.md` ("fazer o Render buildar o próprio Dockerfile a partir do repo").

Consequência: os *deploy hooks*, o `deploy.yml` e o uso da imagem GHCR como fonte de deploy
**nunca chegaram a ser necessários**. Optou-se por **abraçar o auto-deploy** (mais simples para um
projeto acadêmico de um dev só) em vez de reconstruir o pipeline manual. Portanto:

- `deploy.yml` foi **removido** (era um caminho não-funcional e contraditório com o auto-deploy).
- `release.yml` permanece, mas como **gerador de artefatos versionados** (imagem GHCR + build do
  front) para rastreabilidade/rollback — **não** é a fonte do deploy.
- Adicionado `smoke.yml` para a verificação pós-deploy (T11.7).

O trade-off consciente: perde-se o "botão" de escolher *quando* publicar (todo merge na `main` vai
a produção). Aceitável aqui — demos são feitas a partir de branches/preview antes do merge.
